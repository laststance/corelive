publication separately.

## Review corrections

CodeRabbit CLI, in-host adversarial review and outside Claude Code review found
and led to corrections in asset lease ownership, partial asset generation,
packaging resolution, Web env filtering, preload origins, verified HTTP identity,
per-record writes, replay ownership, chained rescue identities and updater
recovery. Pure path relocation was checked separately against original blobs;
CLI review used a transparent path-normalized baseline and scoped passes to stay
within the service's 150-file limit.

The suggestion to refresh category views only when deletion receipts exist was
rejected: remote creates and renames do not create deletion receipts, but must
still appear in active views. Background network failures retry quietly; failed
local rescue or acknowledgement retains an explicit Retry action.

## Dependency security repair

The first pushed migration candidate passed functional CI but Trivy reported six
new vulnerability alerts. The complete dependency audit identified 16 advisory
entries. Updates to Next.js 16.3.8, Sharp 0.35.5, brace-expansion 1.1.21/2.1.7/5.0.12,
source-map-js 1.2.2, fast-uri 3.1.8, http-cache-semantics 4.3.0 and shell-quote 1.12.0
remove the affected versions while retaining existing major-version boundaries.

The remaining upstream `sprintf-js@1.1.3` precision advisory
`GHSA-hp3w-g68c-fv3c` has no published fixed version. The committed pnpm patch
bounds numeric precision to Node's supported range in the package's actual CommonJS
entrypoint, used by the desktop build logger. The regression test fails in four
cases without the patch and passes all five cases, including normal formatting,
with it. The raw version-based audit still reports this one moderate advisory;
it reports no high or critical entries. No blanket audit suppression is added.

## Deployment ordering

The layout migration preserves both original SQL migrations and their snapshots.
Cross-host rescue additionally requires the new additive
`0002_category_deletion_receipts.sql`; it is intentionally not a no-DDL release.
Before the new Web deployment, the branch DB workflow must report exactly this
pending migration in a dry run, apply it, and verify no pending SQL. Existing
application deployments remain compatible with the additive table; rollback does
not drop it. No reset, truncate, or baseline writer is part of deployment.

Vercel retains the existing `laststance/corelive` project, uses `apps/web` as root,
and includes sources outside that root. Production verification uses the deployed
commit and health/canary evidence, separately from the local results above.
