# Expose CoreLive operations to MCP clients on the same Mac

The same-Mac MCP server should let an agent read everything the user can view in CoreLive and perform every operation the app offers, including creating categories and adding tasks. Users register CoreLive once per MCP client on their Mac. That registration applies across projects.

The owner approved storing Dashboard Appearance on the account. Both the dashboard and MCP read and set its theme. On first use, a browser can initialize an unset account preference from its existing selection. LiveEditor keeps its device-specific theme. Human first-use timing for all seven clients remains a five-minute goal. The owner approved opening the implementation PR with those seven timings marked unmeasured. [Implementation QA](../qa/same-mac-mcp.md)

## Writing and dashboard data

LiveEditor is the notepad bundled with the Electron app. Draft reads and edits use the device workspace on the same Mac and work without signing in. The web app provides the account dashboard.

“Add a task” appends an unfinished line to the end of the target category's draft. For a standalone add that omits the category, use the last category selected in LiveEditor on this Mac. If the same request first reads the current note, pass the category ID from that read into the append. Switching categories in the meantime does not redirect the write. If the chosen category is gone, report that nothing was saved there. A fresh workspace starts in `General`. “Record a completed task” adds a completion to the history directly.

Give each distinct user action a descriptive MCP tool name. Adding an unfinished task, recording a completion, and listing completion history each have their own tool. The history tool takes the period and category as filters. Its description states the default date range and category behavior. The shared request uses the same tools available for everyday work.

Candidate catalog names for that request are `read_draft`, `append_unfinished_task`, and `list_completions`. The separate `record_completed_task` creates history directly. A draft read identifies the selected category and returns its current text to the agent. An acknowledged append identifies the saved row and category. A history read identifies the period, time zone, records, and whether the response includes the connected account. Confirm that the client can discover these distinctions through `tools/list` and observe them through `tools/call`.

### Reconciling a task addition after reconnect

The calling agent uses a UUID generator to supply a fresh `operationId` with the first `append_unfinished_task` call and retains that ID in its tool-call history. A separate user request gets a fresh ID even if the task title is identical. Use the [workspace UUID contract](../../packages/desktop-contract/src/offline-workspace-v2.ts) and verify that each client can generate and retain the ID. The user only needs to give the task title.

At the first write, use the category ID from the read for a combined request, or resolve the current selection once for a standalone add. Commit the appended row and its receipt in the same workspace transaction. The receipt must tie the caller's ID and original intent to the authorized workspace, the original category, and the saved row. Capture the category path at save time so a later rename or selection change cannot misreport where the task was added. Today's workspace receipts contain a command digest and revision. The MCP implementation must retain the task-add result as well and continue to read existing receipts. [Receipt schema](../../packages/desktop-contract/src/offline-workspace-v2.ts) and [atomic workspace update](../../apps/desktop/electron/offline/AtomicWorkspaceFile.ts).

After the MCP process exits, the reconnected agent uses the **same ID** in a read-only result lookup, provisionally named `get_task_addition_result`. A matching receipt in the authorized workspace confirms the original save and returns its recorded row and category. A missing, expired, or older receipt without the necessary result yields **unknown**. The lookup never appends a row. A change of account cannot expose the previous binding's result. Reusing a retained ID for a different addition is a conflict.

D8 allows at most one automatic write retry for the original operation when its identity, payload, and remaining retry allowance are established and the write is safe. The caller may retry only while it can establish that its one retry is unused. Losing that state makes another write ineligible. Reconnection starts with the read-only lookup. If the agent loses the original operation ID, it reports an unknown outcome. A missing receipt, a matching title in the draft, or a fresh JSON-RPC request ID cannot justify another write.

## Completion history

Completion history includes a task as soon as its completion is saved on this Mac. When the connected account's dashboard is reachable, the result also includes its completions from other devices. Each completion appears once across the Mac and dashboard. Separate completions with the same title remain separate. For a multi-page account read, fix the account view when its first read starts. All pages in that answer use the same view. A completion that becomes visible on the account afterward belongs to the next request (CEO D4). Read the requested account range and its sync identities together once. The ordinary CoreLive app holds the frozen account range in Mac memory for the initiating read (CEO D5, Eng D4 A). Before releasing each account page, the app checks that the original account binding still applies and sends only the requested page to the MCP helper. Discard the old result on an account change. Release each read when consumed or when its session ends. Read this Mac's records separately and retain the established identity and ownership rules.

Eng D8 A uses the existing authenticated oRPC connection to deliver the account range in finite batches. The server derives the terminal count and batches from the same snapshot-consistent result, including sync identities. CoreLive checks the final record, the expected membership and the current account binding before serving its first account-inclusive page. If the stream is interrupted, discard the partial account result. When device history is readable, return that verified history and identify its scope. Later pages of a successful read use the completed result in Mac memory.

For example, if three tasks were completed today on this Mac and two have synced, “What did I complete today?” returns three tasks. One additional completion from another Mac brings the total to four. When offline or using CoreLive without a connected account, return the history available on this Mac and label that scope in the result.

Merge by identity within the connected account. Account journal rows expose a source and numeric row ID. For a synchronized completion, the account's sync state relates the logical completion ID to the visible completed row. Keep independent Todo rows and legacy rows with no proven link. Titles and timestamps cannot establish identity. Read the local archive for older periods. The dashboard journal uses a fresh offset query per page. An MCP answer spanning several pages needs one coherent account read that includes completion identities and displayed values. The existing [account-scoped range query](../../apps/web/src/server/utils/completedAggregation.ts) is a starting point. If the authenticated account read fails, report the verified device history and its scope. A failure to read the device itself is a tool error. [Journal results](../../apps/web/src/server/procedures/completed.ts), [sync identities](../../apps/web/src/db/schema.ts), and [device archive](../offline-liveeditor.md#size-envelope).

Under Eng D7 A, a verified, non-cancelled device completion whose title an older version did not retain belongs in the ordinary chronological history. Return its known completion time, safe identity and an explicit indication that its title is unavailable on this Mac. Count it once when the requested filters are established. With two named records and one eligible titleless record, an unfiltered day has three completions. After reconnecting, only a positively matched, authorized account record can supply that title. A missing local title provides no evidence of a literal title match.

## Launch and approval

Ship the MCP server inside the signed CoreLive Mac app. Users install CoreLive once and register the same dedicated stdio launcher in each agent they want to use. The launcher runs the fixed, app-owned MCP entry with the bundled Electron runtime in Node mode (Eng D2 A). The ordinary CoreLive workspace owner starts in its normal app mode, including when the helper wakes it. Each guide must name the entry point and arguments verified in the packaged app. Reserve stdout for MCP messages and send diagnostic output to stderr.

Use a private per-user Unix-domain socket between each stdio helper and the Electron main process (Eng D3 A). Only the instance holding the app's existing single-instance lock publishes the socket in a directory private to the Mac user. Verify the peer user and the expected app profile during the handshake. On both ends, the in-process Mac component checks the effective user of the connected peer and hands that same open connection to a Node.js stream. Node owns reads, writes, backpressure and closure after the handoff. Check the expected profile and compatible protocol before dispatch. Distinguish installed, development and explicitly isolated QA data directories. The app selects the current account and workspace. Each client handles its own tool approvals.

Serve discovery from the helper. On the first call that needs the app, connect to the owner, or launch CoreLive with a background-start reason and wait for a compatible, ready owner. Concurrent helpers can request startup, but both must connect to the one lock holder. Handle this reason before the ordinary relaunch path shows a window. Use a bounded readiness wait, with 15 seconds as an initial engineering budget to check on both architectures. A timeout before dispatch means no operation ran. Once dispatched, an interrupted mutation follows its own recovery contract. [Single-instance startup](../../apps/desktop/electron/main.ts) and [second-instance handling](../../apps/desktop/electron/DeepLinkManager.ts).

When a request needs CoreLive and the app has quit, the MCP integration starts it in the background. Adding a task leaves keyboard focus in the client. An explicit request to open LiveEditor shows its window.

Each of the seven clients uses its own tool approval settings for CoreLive operations, including deletion and restart. Once the client permits a call, CoreLive applies its usual account, data, and save checks without prompting the user to confirm the same operation again.

## Errors an agent can act on

For a failed tool execution, return `isError: true`, a common error code, structured fields for the operation, its effect and the next action, and a short readable explanation. Use the same meanings in all seven clients. For an interrupted write, distinguish a definite refusal from an unknown outcome. A confirmed write returns success. If the server executable never starts, the client owns the launch diagnostic and there is no tool result. [MCP tool errors](https://modelcontextprotocol.io/specification/2025-11-25/server/tools#error-handling) and [stdio framing](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports#stdio).

The following examples specify intended behavior. The MCP server has yet to produce live responses.

Ask which category to use if the user's explicit target has gone.                                                             |

## Error path review

The initial plan omitted actionable tool errors. In particular, a missing recovery action for a stale revision and a missing trace for a dropped worker reply capped the initial error score. The desktop has reason codes for both. No MCP error transcript exists yet. In this matrix, **specified** means the reviewed design states the requirement. Verification needs a real tool response.

| Path           | Class                    | What happened | Safe fix  | Recovery and effects     | Code      | Context                          | Trace                | Redaction | Channel                               |
| -------------- | ------------------------ | ------------- | --------- | ------------------------ | --------- | -------------------------------- | -------------------- | --------- | ------------------------------------- |
| Category gone  | Explicit target rejected | Specified     | Specified | Unchanged                | Specified | Category ID                      | N/A                  | Specified | MCP tool error                        |
| Stale revision | Conflicting edit         | Specified     | Specified | Unchanged                | Specified | Category and revisions           | N/A                  | Specified | MCP tool error                        |
| Undo expired   | App refusal              | Specified     | Specified | Unchanged                | Specified | Completion ID                    | N/A                  | Specified | MCP tool error                        |
| Worker stopped | Unexpected interruption  | Specified     | Specified | Unknown until reconciled | Specified | Version, operation and component | Safe trace reference | Specified | MCP tool error if the bridge is alive |

Expected refusals need no crash trace. If the stdio process exits, the host reports the transport loss. After reconnect, the agent looks up the original operation ID under D13. D8 bounds any safe write retry. The acceptance tests use synthetic identifiers.

- **CAP6:revision-conflict:fix** — “The draft in category C1 changed from revision 9 to 10. This edit made no change. Read the current draft before retrying.”
- **CAP6:worker-unavailable:trace** — “The workspace worker stopped while adding the task. Reconnect and check the original operation ID. If the save record is unavailable, report the outcome as unknown.” The structured result and the redacted diagnostic share the operation reference.

### Acceptance checks

- **Registration and updates.** In an isolated Mac environment, start each client with CoreLive installed and unregistered. Confirm that its user-wide entry works in a second project. Repeat a real call through the original registration after an in-place app update. Verify the launcher, embedded runtime mode and signature in the signed DMG and ZIP for Intel and Apple Silicon, including the macOS 13.0 floor. With CoreLive closed, stdio discovery leaves it closed. The first data operation wakes the normal app in the background and preserves client focus. Repeat with CoreLive already running. Start the test timer with the app in the installation state stated in the guide. Record first-run OS prompts and startup delays within the trial.
- **First use.** Open the selected instructions, register the released app, and send the shared request with a distinctive task title. Capture the answer, saved category, unfinished row, history entries and scope. Time each of the seven runs independently. Record client and CoreLive versions, account state, any reload or approval, elapsed time and the outcome. The five-minute design budget allows one minute for reading, two for registration and reload, and two for the request, approvals and answer.
- **Concurrent edits.** Have a renderer with pending input and two client processes target one category. The user's typing survives. Each intended append appears once. A conflict or failed flush leaves the draft recoverable. Observe the running editor receive the owner's published revision and retain pending input.

### Section 10. Maintenance over the next year

The lasting dependencies are the public tool names, the installed command path, and the meaning of receipts and history results. The accepted shape keeps discovery in the stdio helper. The ordinary app owns the workspace transaction and selects the current account. A single account read can outlive one page delivery. The app holds its frozen range until consumption or session disposal. Overlapping reads increase the app's peak memory. PNG rendering and decoding can temporarily hold both representations. T3 and T4 measure those costs. If the app or helper drops a connection, dispatch state and durable receipts determine what can be reported. See the [failure and recovery cases](#section-2-errors-and-recovery) and the [Mac release checks](#acceptance-checks).

```text
list tools  -> helper -> shared catalogue
call tool   -> verified local connection -> ordinary app checks profile and account
  append    -> flush editor -> workspace command + receipt -> committed revision -> reply
  history   -> one authenticated range -> app holds this read -> recheck binding -> page
  day PNG   -> eligible day -> renderer data URL -> app decodes -> publish file -> path
```

| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Shallow module                 | DX D10 exposes one tool for each user-visible outcome. An append hides editor flush, durable write and publication behind a single call. Discovery is usable before the app starts.                           |
| Information leakage            | Eng D3 and D5 keep socket ownership and the image encoding inside the app integration. Public outputs carry the saved row and category, scoped history, or the confirmed file path.                           |
| Temporal decomposition         | The workspace command commits the mutation and its receipt together (DX D8/D13). Flush and publication retain their places in the editor's existing workflow.                                                 |
| Pass-through methods           | The helper parses tool inputs and reports effects. The app owns eligibility and writes. The alternative standalone service above would duplicate coordination and introduce another state owner.              |
