Diagnosis from the session: this is not an idea shortage, it is the absence of a sorting criterion. ## Demand Evidence

- n = 1. Q1 answer: 「自分が毎日使っていて消えたら困る」. README states pre-launch, zero users. No waitlist, no interest claims, nothing inflated.
- What he would scramble to replace first: 「LiveEditor の書いて Cmd+Enter で完了する一連」 — the write → Cmd+Enter → line becomes a Completed record loop. Not the heatmap, not Floating, not skill-tree.
- Second nameable user: none. 「自分だけ。具体名は出ない」.
- Corroboration from git: the last three months of commits (v0.20.x → v0.21.0) are almost entirely LiveEditor completion / clear / sound / shortcut fixes. The place being repaired is the place being used daily.

## Status Quo

Before CoreLive: 「メモ・テキストファイルに書いて消していた」. The cost was not time, it was the trace: nothing accumulated, so the day ended with no evidence of having done anything. The real competitor is a text file, not Things 3 or Todoist.

## Target User & Narrowest Wedge

- **User #1**: Raphtalia. Solo developer, writes-and-deletes, wants end-of-day self-affirmation without being graded (North Star: 「些細でも経験値、今日自分頑張ったなと自分を肯定できる感覚」).
- **User #2**: unnamed today. Chosen strategy (Approach C below): remove the login wall so a stranger can run the loop within 60 seconds of landing. This answers the Q4 bonus push "what if the user didn't have to do anything at all?" literally.
- **Wedge**: `corelive.app/write` signed out (eng review D14: a new public route, not `/live-editor`). Write a line, press Cmd+Enter, the line is kept on the device, and a small ember above the editor (the first thing on the page, design review DR1) says "3 things kept today". The footer reads "Kept on this device." with a quiet "Sign in" link to `/login?redirect_url=/write` (Clerk's login surface carries the sign-up link, and prod sign-up stays Turnstile-gated, which is fine for a human stranger). The link is never framed as "save".

## Constraints

- **Never grade, never shame** (DESIGN.md, non-deviable): no streaks, completion rates, KPI percentages, social comparison. Landscape evidence backs this: streak mechanics produce "streak creep", satisfaction drops after day 90, and users abandon rather than restart after a break.
- **Route gating today**: `src/proxy.ts` protects `/home`, `/skill-tree`, `/live-editor`, `/settings` (a static `createRouteMatcher` list; anything not listed is public). `/floating-navigator` is intentionally public and renders a signed-out front-door card (`FloatingNavigatorContainer.tsx` gates on `useUser().isLoaded` / `isSignedIn`) — the precedent for a public route with a signed-out state.
- **Packaged Electron panel contract**: the LiveEditor panel loads the remote `/live-editor` route and its ONLY signed-out signal is a navigation to `/login` or `/sign-up` (`AUTH_PATHNAMES`, `electron/WindowManager.ts:1041-1056`): on that redirect it hides the panel and falls back to the Floating OAuth front door. Installed builds have a frozen main process, so `/live-editor` must keep producing that server-side redirect. Resolution (eng review D14): the signed-out web editor lives on a **separate public route `/write`**; `/live-editor`, `src/proxy.ts`, `src/app/live-editor/page.tsx` and `electron/` are untouched. Real signed-out parity inside the panel needs a main-process release and is out of scope here.
- **Clerk readiness hooks**: `useClerkQueryReady` returns `false` while signed out; any signed-out render must gate on `useUser().isLoaded` / `isSignedIn` instead, or the page spins on "Loading…" forever.
- **Clerk force redirect overrides `redirect_url`**: `NEXT_PUBLIC_CLERK_SIGN_IN_FORCE_REDIRECT_URL=/home` is set (`.env.example:13`, required by `src/env.mjs:23`), and Clerk documents that a force redirect URL "will override the `redirect_url` value if present". Today the login page renders `<Login fallbackRedirectUrl="/home" />` (`src/app/login/[[...login]]/page.tsx:101`) and relies on its own hard `window.location.replace(resolvePostLoginPath(...))` effect racing Clerk's soft navigation. The fix is to pass the resolved path as `forceRedirectUrl` (the prop takes precedence over the env var and the search param).
- **Signed-in web `/live-editor` today** renders the "LiveEditor is available in the CoreLive desktop app" notice (`LiveEditor.tsx:2057-2063`, reached from `AppSidebar.tsx:207`). The component is preload-bound: 15 `getLiveEditorAPI()` call sites, `activeCategoryId` waits on the preload `Promise.all`, the textarea is disabled until then (`:2074-2077`), and notes load only through `api.note.get`. The preload surface is already an interface, `LiveEditorAPI` (`electron/types/electron-api.d.ts:633-700`); the web needs an implementation of it, not a new abstraction (eng review D1).
- **`useSelectedCategory` rejects non-positive ids**: its `getSnapshot` drops `0`, so the signed-out sentinel category cannot flow through it (outside voice #3); the sentinel is set directly in `LiveEditor.tsx`.
- **Pre-launch freedom**: schema / API breaking changes are allowed (README). No migrations to preserve.
- **No-dedup principle**: repeating a task is a habit signal, never collapse identical titles. Accidental double submission still needs an idempotency key. The `ImportBatch` model exists in the schema but its write path was deleted in v0.21.0 (`157320ab`); nothing in `src/server` writes it today.
- **`createCompleted` has no `completedAt` input**: merged rows would all bucket on sign-in day (`completedAt ?? createdAt`). `Completed.categoryId` is required (`onDelete: Restrict`), so a merge must resolve the account's `Category.isDefault`.
- **Streak residue still ships**: `calculateStreaks` in `completed.ts`, `useStreakNotifications.ts`, `calc-streak.ts`, "longest streak" in `YearInReviewModal.tsx`, `AchievementAnimation.tsx`. Handled in Later.
- **Test infrastructure**: E2E / Playwright was removed in PR #167 (`2558b90f`); `pnpm validate` is vitest only. Any gate must name vitest suites or a `playwright-cli` recording.

## Premises

Agreed in session. #2 revised after the Codex cold read; #4 replaced by the Approach C choice.

1. The roadmap problem is the lack of a sorting criterion. The deliverable is one criterion plus a short Now / Next / Later list, not a new feature.
2. Core = the LiveEditor write → Cmd+Enter loop. **Reward = seeing "it was kept" right where you pressed.** The yearly heatmap is the long-horizon reward; its pull on daily use is unproven. **Criterion: does this make the daily loop faster, more reliable, or show the keep immediately?**
3. The promise is "a scratchpad that never forgets what you crossed out". Streaks, completion rates, and grading are permanently out of scope.
4. (revised) n = 1 today. User #2 is created by removing the login wall, not by handing a DMG to a named person. Onboarding beyond the signed-out page stays deferred until one named person has actually used it.
5. Anything that touches neither the loop nor the reward (skill-tree, more themes, more windows) is a deletion candidate, not a polish candidate. Continue the v0.21.0 core-only direction.

## Landscape (generalized web search, 2026-09-02)

- **Layer 1**: heatmaps are commodity in 2026 habit trackers (Habitify, HabitBox, Streaks) and are almost always paired with streaks.
- **Layer 2**: streaks backfire — "streak creep", day-90 satisfaction decline, abandon-after-break, dread replacing pride. "Done lists" are recommended for motivation; Todoist's "64% completed" made a reviewer feel like a failure. Done-list apps exist (MyDone) but are manual journals.
- **Layer 3 / eureka**: the category assumes fear-of-breaking-the-chain motivates; the evidence says the chain is the churn mechanism. CoreLive keeps only unbreakable accumulation: a bad day is an empty cell, not a failure. And because the write-and-delete user's pain is on the input side, the scratchpad → done-list pipe (Cmd+Enter) is the differentiator, not the heatmap.

Sources: The Decision Lab "Streak Creep"; Klarity "Why Streak Features Fail ADHD Users"; Yu-kai Chou "Streak Design: Motivation Without Burnout"; Medium "Keep To-Do lists aside, go with Done Lists"; XDA "I deleted my to-do list apps for a week"; HabitBox "Best Habit Tracker Apps 2026".

## Cross-Model Perspective (Codex, cold read, read-only repo access)

- **Steelman**: CoreLive is not task management; it is a 「痕跡を失わないスクラッチパッド」 for people who write and delete. Cmd+Enter alone turns a temporary memo into a permanent Done record, returned as a warm year, with no management overhead.
- **Most revealing answer**: 「LiveEditor の書いて Cmd+Enter で完了する一連」 — the only answer with replacement demand. The input → complete → erase pipe is the product; the advantage is saving without making the user conscious of recording.
- **Challenged premise**: "Heatmap is the reward." The evidence only supports "the trace remains"; there is no evidence the yearly heatmap strengthens daily use. Accepted → premise 2 revised. Codex's proposed 2-week hide/show experiment was rejected (n = 1, mood-confounded); building the ember and watching whether `/home` gets opened less is the cheaper test.
- **48-hour proposal**: "Today Ember" inside LiveEditor — a small today cell under the editor, updated after a successful Cmd+Enter; revert on undo / save failure; no new DB change; tests for success, failure, undo, double-fire; QA in the packaged Electron panel. Adopted with two corrections from the spec review: `useHeatmapData` cannot serve a signed-out ember (it is `enabled: isClerkQueryReady`), so the ember reads a source-switching hook instead; and the ember is today-only (no strip).
- **Independent agreement with premise 5**: Codex's skip list dropped #53, #120 and #124 without seeing the conversation.

## Approaches Considered

- **A) Ember-first, delete-second** (S / Low). Today Ember as the single Now item, deletion decisions Next, one named observer Later. Rejected by the user: it leaves the number that is actually zero (users) untouched.
- **B) Loop / Reward / Trace ladder** (M / Med). One item per layer per cycle. Rejected as a framework (too much structure for n = 1); the three-word vocabulary is borrowed for `docs/ROADMAP.md`.
- **C) No-login LiveEditor**. **Chosen.** Sized L at choice time (Completeness 6/10); the spec review re-sized it to XL because of a host-adapter extraction; the eng review cut it back to **L** by reusing `LiveEditorAPI` as the host contract (D1) and shipping the signed-out page on a new public route (D14). Split into two PRs (web host + route first, ember second). Ceiling and upgrade trigger recorded below.

## Recommended Approach: C — no-login LiveEditor, with the ember inside it

Wireframe (signed-out state, two screens, today-only ember): `~/.gstack/projects/laststance-corelive/designs/sketch-signedout-liveeditor-20260902.png`.

### Rules that hold everywhere

- **Auth gate**: `/write` and the component gate on `useUser().isLoaded` / `isSignedIn` (Floating pattern), never on `useClerkQueryReady`, which is `false` while signed out.
- **Route split (D14)**: `/write` is a NEW public route (`src/app/write/page.tsx`); it is public by construction because `src/proxy.ts` only protects its static list. `/live-editor`, `src/proxy.ts`, `src/app/live-editor/page.tsx` and everything under `electron/` stay byte-for-byte. The packaged panel therefore still receives the server-side `/login` redirect on `/live-editor`, hides, and falls back to the Floating OAuth front door exactly as today. No user-agent sniffing, no Electron client header, nothing to rip out when the panel gains parity later. Signed-out browser visitors never trigger server writes; everything is client-side until sign-in.
- **One host contract (D1, D7)**: the existing preload interface `LiveEditorAPI` IS the host contract. A single resolver, `getLiveEditorHost()` in `src/lib/live-editor/liveEditorHost.ts`, returns the preload object (through `getLiveEditorAPI()`, which already handles the legacy `window.brainDumpAPI` name) when `isLiveEditorEnvironment()` is true, and the web implementation otherwise. `isElectronLiveEditorPanel()` wraps the same check for chrome decisions. The 15 `getLiveEditorAPI()` sites in `LiveEditor.tsx` swap to `getLiveEditorHost()` with no change in call shape, so the existing `LiveEditor.test.tsx` suite passing unchanged is the Electron no-regression proof.
- **Signed-in web gets the editor**: the desktop-only notice is replaced by the same editor with server completions and device-local notes. Success criteria therefore say "packaged Electron signed-in path has no regression" (the ember is its one visible addition), not "web unchanged".
- **Theme = token slots only (design review DR8)**: `/write` uses `bg-background` / `bg-card` / `text-foreground` / `text-muted-foreground` / `border-border` / `--hm-*` / `--ring` and nothing literal (no `zinc-*`, no hex); it inherits whatever `data-theme` the visitor has (default Warm Cathedral light, `System` follows the OS). No route-level `forcedTheme`, no new theme, DESIGN.md rule 1 untouched. The approved mockup (`variant-F.png`, rendered in the shadcn default dark palette) is the approval of the layout, structure and copy; its colors are what the Graphite Dark theme produces, not a spec. "shadcn default font" resolves to the app's `font-sans` (Inter Tight), never a literal `system-ui` stack; the wordmark is plain 13px semibold, normal case, `text-muted-foreground`.

### Now — PR-1: `/write` + web `LiveEditorAPI` host + local store + completion writer

1. **`src/lib/live-editor/liveEditorHost.ts` (D7)** — `getLiveEditorHost(): LiveEditorAPI` and `isElectronLiveEditorPanel(): boolean`. Web host: `note.get` / `note.set` read and write `corelive.local-note.v1` keyed by category id; config-ready resolves immediately (so the existing `Promise.all` marks the editor ready with no preload); last-category returns nothing (web derives the category itself, see 3).
2. **Local stores (D2, D5, D6)** — `src/lib/live-editor/localCompletionStore.ts` (`corelive.local-completions.v1`) and the note map. Every write is read-modify-write on the raw string, parsed through a zod schema (corrupt or foreign values are treated as empty, never thrown); a `storage` event listener notifies subscribers so two signed-out tabs agree; `getSnapshot` returns the raw stored string (referentially stable) and counts are derived in `useMemo` keyed on it. Storage availability is probed ONCE at module init (`setItem` / `removeItem` of a probe key); on failure (private mode, quota, disabled) the store falls back to an in-memory map for the session and exposes `storage: 'unavailable'` so the ember can say so, at most one notice, never one per keystroke.
3. **Category derivation (D2, D3, outside voice #3)** — `LOCAL_CATEGORY_ID = 0` (numeric sentinel, `src/lib/live-editor/constants.ts`). Local completion ids are `crypto.randomUUID()` strings; `LiveEditorCompletionId = Completed['id'] | string` (indexed access on the Prisma type, no new id type).
4. **`useCompletionWriter()` (D9, D16)** — the one chokepoint that replaces the three `mutateAsync` sites (`LiveEditor.tsx:1156`, `:1241`, `:1808`): signed in → `completed.create` / `completed.delete` as today; signed out → `localCompletionStore.add` / `.remove`. Double-fire safe: the existing lifecycle guard (`pending` / `undone` / `confirmed` / `restored`) is reused, not duplicated.

### Local store spec (signed out)

- `localStorage` keys: `corelive.local-completions.v1` = `{ version: 1, items: [{ id (uuid), title, completedAt (ISO), mergedBatchId? }] }`; `corelive.local-note.v1` = `Record<string, string>` keyed by category id, with `"0"` (`LOCAL_CATEGORY_ID`) as the key for the implicit signed-out category (same map shape as `electron/LiveEditorNoteStore.ts`). IndexedDB only if a year of one-line entries ever exceeds the quota (it will not).
- Validation: one zod schema per key; anything that fails parsing is read as empty and overwritten on the next write. Writes are read-modify-write on the raw string; cross-tab sync via the `storage` event.
- "Today" = items whose `completedAt` falls on the local calendar day (same keying as the server's local-day bucket, which receives the browser `timezone`); the ember re-derives at the `useLocalDayKey()` tick.
- Undo deletes the local record by `id` and decrements the ember.
- Unavailable storage (probe fails once at init): in-memory fallback for the session, `storage: 'unavailable'`, one notice.

### Ceiling and upgrade trigger (recorded because the choice was 6/10)

- Device-local storage can be lost when browser storage is cleared; no multi-device until the merge ships.
- Safari ITP purges script-writable storage, `localStorage` included, after 7 days without site interaction; a signed-out stranger returning in two weeks can lose the trace. The merge in Next is the upgrade path.
- Signed-out mode is web-browser only; the packaged panel keeps today's front-door fallback because `/live-editor` is untouched.
- Two signed-out tabs pressing Cmd+Enter in the same instant can lose one write (browser `localStorage` has no cross-process mutex in Chromium). Accepted: one human, one keyboard; the `storage` event keeps the two embers in agreement after the fact.
- Upgrade when a second person actually uses the page (then merge + durability first), or when the panel needs signed-out parity (main-process release).
