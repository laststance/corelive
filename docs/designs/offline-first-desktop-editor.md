## Problem Statement

CoreLive is a desktop editor app. It must be fully usable offline without ever signing in; signing in only adds the optional web dashboard (Issue #216, owner product design). Today, re-verified on `origin/main` @ `ae6c8222`, this branch's base. The issue's own table cites the owner's local `main` @ `3cd1f47a`, which only removes `mise.toml`. All line references below are against `ae6c8222`:

1. A Mac that never signed in shows "Connect once to prepare this Mac." and cannot write (phase `needs-preparation`, `OfflineEditorController.ts:130-141`). Preparation retries forever with backoff up to 60 s, rebuilding a hidden `/desktop-auth` window each time (`:685-727`).
2. Explicit sign-out locks the workspace (`signOut()` `:355-384` → `registry.lock()`; phase `locked`). Reopening it needs the same account online.
3. The Settings window loads the remote, Clerk-protected `${serverUrl}/settings` (`WindowManager.ts:1250,1357`, `proxy.ts:9`). Its desktop UI lives in `apps/web/src/components/electron/*` (≈5.8k lines including tests).
4. Category create/rename/delete is online-only (`NativeEditor.tsx:173,316`; `OfflineEditorIPC.ts:157-177`). `EditorCategory.id` is the server serial id, so a category cannot exist before the server creates it.
5. Desktop-only editor internals (`./surface`, `./store` DurableEditorStore, `./input`, `./draft-edits`, `rowIdentity`, …) live in the shared `packages/live-editor`.
6. Project docs still say "Electron loads `https://corelive.app/` directly".

## What Makes This Cool

You open the lid on a plane: no network and no account. CoreLive opens straight into the editor. You write a line, press Cmd+Enter, and it is kept. Weeks later you sign in once, and every keep appears on the corelive.app heatmap on its original day. Signing out never takes the writing away. The daily loop (ROADMAP criterion: write a line → Cmd+Enter → kept) no longer depends on anything outside the Mac.

## Constraints

- macOS only. Pre-release, single user (`/CLAUDE.md` 2026-09-29), so breaking contract and schema changes are allowed and no compat shims are needed for other users. The owner's own existing workspace **must** migrate losslessly.
- Bundled documents keep CSP `connect-src 'none'`, `sandbox: true`, context isolation and IPC sender validation. Never weaken `webSecurity`, CORS or origin checks. Every network call goes through the main process.
- Tokens never enter workspace files. A remembered account id is never a credential.
- QA must not take over the host: no host mouse, keyboard, focus or installed CoreLive; no real-account login loops; no login E2E suite. Use headless fixtures, unit and integration tests, and an isolated dev instance driven by agent-desktop semantic AX. Native QA in the VM needs the owner's go-ahead.
- One request = one pipeline: #216 ships as one PR. No phased plan.
- DESIGN.md north star: being local-only is a calm, valid state, never a nag ("Saved on this Mac", not "Sign in to save").

## Premises

1. **One device workspace, always usable.** Each Mac has exactly one account-less workspace. There is no preparation phase and no account gate. Controller phases shrink to `ready | recovery`. Recovery is the storage-fault or corruption path, which keeps copy and export.
2. **Sign-in attaches sync; sign-out detaches it.** Sign-in reconciles categories, then uploads unsent completions to the attached account. Sign-out flushes, stops sync, ends the Electron Clerk session and leaves the same workspace editable.
3. **One bound account per Mac.** Writing is never partitioned or locked by account. The device binds to the first account it attaches to (`binding.accountId`), and the binding survives sign-out. Signing in again with that account resumes sync.
   - Signing in with a different account does not attach sync. Settings ▸ Account says, calmly, "This Mac syncs with <email>. Sign in with that account to sync it", and editing is unaffected.
   - Moving a Mac's writing to another account is not part of this product today (single user, pre-release).
   - Operations in flight or uncertain at sign-out stay with the bound account and settle by receipts on the next attach (the 10-21 rule: a payload that may have reached a server is never re-sent elsewhere).

4. **Categories are local-first.** A category has a stable local id plus an optional server id for the bound account. Offline create, rename, recolor and delete are written to the outbox. Server root and child names are unique per user and parent (`Category_root_name_userId_key`, `Category_child_name_parent_userId_key`), so a replayed create adopts the existing category of the same name path instead of duplicating it.
5. **Settings is bundled.** `settings.html` is served from `corelive-editor://app/` with a sandboxed preload. All persistence is native: device workspace preferences plus `config.json`. A new Account section offers Sign in, Sign out and Open dashboard.
6. **The editor code belongs to Electron.** Desktop-only modules move from `packages/live-editor` to `apps/desktop/renderer`. The package keeps only what the web dashboard also imports.
7. **Docs tell the new truth**: README, `docs/*` and the local `CLAUDE.md`.
8. **QA without takeover** (see Success Criteria).

## Approaches Considered

### Approach A: Local pseudo-account (minimal)

Keep account partitions and add a synthetic `local` owner used when no account is active. Sign-out switches to the local workspace. Settings stays remote. **Rejected:** the writing visibly disappears on sign-out, which contradicts AC2, and Settings still fails offline (AC3).

### Approach B: Device workspace v2 + local category ids + bundled Settings + code move (ideal) — **chosen**

One workspace per Mac, sync as an attachment and local-first categories. Settings ships inside the app and the editor code moves to `apps/desktop`. Effort XL, risk Med (data migration, category reconciliation). It reuses AtomicWorkspaceFile, the workspace worker, CompletionSyncLoop, the `completed.sync*` receipts, `localEditorProtocol`, TokenBroker, OAuthManager and the existing Settings components. After the CEO dual voices, it adopts the "B-lite" account model: one bound account per Mac (P3), with no per-account bindings or account-switch machinery.

### Approach C: SQLite device store (lateral)

Replace the JSON workspace with a SQLite file. **Rejected:** it adds a native module to the electron-builder + pnpm asar packaging (known to drop leaf deps). It also rewrites a durable store whose atomic and recovery behavior is already proven by tests. Data volume does not need it yet.

## Recommended Approach — decisions (B)

**D1 Device workspace.** Store it at `userData/offline/workspaces/device.json` with recovery copy `device.recovery.json`, keeping the AtomicWorkspaceFile envelope with `ownerId: "device"`. The schema becomes `OfflineWorkspaceSchema` **version 2**:

- `ownerId` and `preparedAt` are replaced by `createdAt`.
- `selectedCategoryId`, category references, `categoryMoves`, `categoryDeletions` and recovery-copy `categoryId` become **local category ids** (UUID strings).
- A new `binding: AccountBinding | null` is added, set at the first attach and kept after sign-out (P3). `AccountBinding = { accountId, displayEmail, serverCategoryIds: Record<localId, number>, base: Record<localId, { name, color, parentLocalId }>, declined, deletionReceipts, lastSyncedAt }`. `base` is the last server state seen and is the merge base in D4.
- Marking an outbox entry in flight happens in the same transaction as the binding check, before the request leaves the main process. Only the bound account's session can send.

**Size budget.** In local-only mode completions never retire, because retirement needs a server checkpoint (`WorkspaceService.checkpoint`). The local workspace is the only record, and it is what uploads on sign-in. The estimate:

- _Input:_ 20 completions per day [estimated].
- _Growth:_ about 4.6 MB per year [measured, below].
- _#216's own addition:_ the binding and the category outbox are O(categories), under 10 KB for 50 categories.
- _Measured_ (2026-11-03, Apple M4 Max, a `/tmp` benchmark of the real envelope path: serialize → SHA-256 → write → fsync → rename → directory fsync; about 640 bytes per completion):
  - 3,650 completions (1 year at 20/day): 2.3 MB, p95 18.1 ms
  - 10,000 completions: 6.4 MB, p95 30.9 ms
  - 36,500 completions (5 years): 23.2 MB, p95 78.4 ms
- _Decision:_ keep one snapshot file. With C28, retirement keeps each completion's text, so the workspace grows at about the same rate signed in or not. Five years still stays under the 100 ms "instant response" threshold (RAIL).
- _Gate:_ a worker benchmark test builds a 36,500-completion local-only workspace and asserts the keep commit stays at p95 ≤ 100 ms on the owner's Mac. The measured numbers go in the PR, and `docs/offline-liveeditor.md` states the envelope.

First launch creates the workspace with one local default category `General` (`DEFAULT_CATEGORY_SEED`, `isDefault: true`). The worker accepts only `ownerId: "device"`. **Delete:** `needs-preparation`, `preparing` and `locked` phases, `prepare()`, `preparationFailed` + retry loop, `assertFirstPreparation`, `waitForSettings`, the "Connect once" and "Sign in with the same account" scenes in `NativeStateScene.tsx`, and the dead `LiveEditorNoteStore.ts`.

**D2 Registry v2 = sync attachment.** `OfflineAccountRegistry` stores `{ version: 2, deviceId, attachedAccountId: string | null }`. `authenticated(clerkId)` (`main.ts:367-370`) attaches in this order:

1. Persist `attachedAccountId`.
2. Reconcile categories (D4).
3. Start CompletionSyncLoop.

Sync health is a separate status from the editor phase: `local-only` (no account), `syncing`, `waiting` (offline/backoff, with count), `sign-in-to-sync` (401 or expired session) and `synced`. The status line copy follows the 10-21 calm set: "Saved on this Mac" is shown for `local-only` and is never an error. `sessionUnavailable` only pauses sync. The `offline-editor-retry` IPC becomes a sync retry and never touches editing.

**D3 Sign-out works offline.** A new Settings ▸ Account ▸ Sign out, plus the existing `auth-logout` path, runs these steps in order:

1. **Local flush.** The pending editor autosave is committed to disk. This uses no network. A failed disk commit cancels the sign-out with "Not saved — retry or copy your writing" (unchanged rule). Unsent operations do **not** block sign-out. They stay in the outbox for the bound account (P3).
2. `loop.stop()`, then `attachedAccountId = null` persisted in the registry.
3. **Best-effort remote revoke, online only.** The TokenBroker's hidden window calls `Clerk.signOut()` through its preload with a 5 s timeout. A timeout or offline state skips this step and never fails sign-out.
4. **Local session end, always.** The login window, Settings and the TokenBroker all use Electron's default session (no `partition` anywhere). Main removes the cookies for the app domain (from `serverUrl`) and the Clerk Frontend API domain (from the publishable key: `clerk.corelive.app` in production, the `*.clerk.accounts.dev` host in development). It also calls `session.defaultSession.clearStorageData` with `storages: ['cookies','localstorage','indexdb','serviceworkers','cachestorage']` for both origins. Then `broker.reset()` destroys the hidden window.

The editor stays `ready` with identical content. **Invariant, verified by the C15 read-back:** after step 4 this Mac holds no Clerk client cookie or session token, so no credential can be minted without a fresh sign-in. If the read-back still finds one, the event is logged and sign-out still completes. Offline, the server-side session simply expires on its own. Verification is a contract test with a fake `session` (asserts both origins and storage kinds were cleared, and that a reset broker reports `signed-out`) plus a controller test proving sign-out completes with the network failing and with unsent operations present.

**D4 Local-first categories.**

- _Outbox:_ category operations (C11 shapes), derived by the merge (C19), join completion operations in the same atomic transaction. They are sent before any completion that references the same local id.
- _Server:_ a new `category.syncApply` procedure, account-scoped.
  - **Idempotency key:** `(userId, operationId)`, reusing the existing `CompletionSyncReceipt` table, which is renamed `SyncReceipt` in the same migration. Its `outcome` column type becomes a discriminated union in `packages/desktop-contract`: the existing completion outcome plus a category outcome (`applied { serverId }`, `adopted { serverId }`, `name-taken`, `invalid-parent`, `conflict { current }`). The contract types and offline-sync schemas are renamed with it. "No API change" applies only to the `completed.sync*` wire format. It stores `payloadDigest` + `outcome`. A replay returns the stored outcome; a digest mismatch returns `digest-mismatch`.
  - `create` resolves the name path: adopt an existing same-path category or insert a new one, and return its server id.
  - `rename`, `recolor` and `reparent` act on the server id.
  - `delete` sends source and destination as server ids. It reuses the existing rescue semantics (`categoryDeletionTable`, positive ids) and stays receipted.
- **Dependency rule (send order).** An operation is sendable only when every local id it references has a server id in the attached account's binding. In practice:
  - a parent's `create` before a child `create` or a `reparent` onto it
  - the destination's `create` before a `delete` into it
  - a category's `create` before `rename`/`recolor` and before any completion that uses it

  Within one category, operations go in local commit order. A dependent waits, and is never reordered or dropped.

- **Merge rule (three-way, per account).** On attach, and after each category refresh, compare local state, the server list and that account's `base`. A field changed only on one side takes that side's value. A field changed on both sides is resolved **without clocks** by a server-side compare-and-set. Each `rename`/`recolor`/`reparent` operation carries `expected`, the base value of that one field. The server applies the change only when the current field still equals `expected`. Otherwise it returns `conflict { current }`, so no client or server timestamp, and no row-level `updatedAt`, decides which data wins.

Server-side edits are a normal path, not a rare one. The web dashboard sidebar still manages categories (`AppSidebar.tsx` mounts `CategoryManageDialog`; `useCategoryMutations` calls `category.create/update/delete`), and another Mac can edit them too. #216 does not change web category management.

A server `delete` promotes the deleted category's children to roots and moves its records to the destination (`deleteCategory`). The local mirror applies the same promotion.

**Where the destination comes from.** Every `category.delete`, from the web sidebar or a Mac, commits a `CategoryDeletion { sourceId, destinationId }` row in the same transaction (`category.ts`: "The receipt commits with deletion, preserving the chosen destination for other hosts"). `completed.syncBootstrap` returns those rows as `deletions`, and it runs on attach and on each category refresh. That is how the mirror learns a server-side deletion and its destination, with no desktop `operationId` involved. Chained deletions resolve through the existing chained-move resolution. If the chain ends at a category the account no longer has, the destination falls back to the local default category, with an entry in sync details. Records are never silently dropped.

**Local records of a removed category.** Recording `categoryMoves[source] = destination` (the existing chained-move map) re-targets everything:

- kept local completions and retired history resolve their category through it for display and Today Ember
- a provably unsent completion create is revised to the destination
- an uncertain or sent completion that the server rejects with `category-removed` (`completionSync.ts:161-162`) gets the 10-21 revisioned move of the same completion identity
- Undo restores into the resolved destination, never the retired source

| Case                                                                                                   | Result                                                                                                                                                                                                                                                                                                                   |
| ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Server renamed/recolored/reparented; local unchanged                                                   | Apply the server value locally; update `base`                                                                                                                                                                                                                                                                            |
| Local changed; server unchanged                                                                        | Send the operation                                                                                                                                                                                                                                                                                                       |

The local value is **kept, not discarded**: sync details list it as "This Mac's name/color/parent was not applied" with an "Apply this Mac's value" action, which queues a fresh operation whose `expected` is the new server value |

Its children become roots, mirroring the server                                                                                                                                                                                                      |

- _Attach reconciliation:_ an account with an existing binding is merged against its `base`. An account without one matches by name path first; the local default matches the server `isDefault`. Either way the merge table above then applies.

**D7 Upgrade migration (v1 → v2), run once, before the first v2 open.**

1. _Pick the source:_ the workspace of `activeAccountId ?? lastAccountId`. If none exists, create fresh.
2. _Convert:_ give each category a new local id and record `serverCategoryIds` bound to that account. Rewrite every category reference in drafts, completions, retired completions, outbox, moves, deletions and recovery copies through that map. Operations keep their `opId`, revision and receipts, and ones already sent stay bound to that account (P3). Selection, Undo eligibility deadlines and the count checkpoint are preserved.
3. _Bind the account:_ create `binding` for the source account from the old server ids and categories (as `base`). Set `attachedAccountId` to the old `activeAccountId`, or null if the legacy v1 state was `locked`. A later sign-in with that account merges against its `base` instead of re-matching by name.
4. _Write a receipt:_ record the migration receipt inside v2 before replacing the registry.
5. _Keep the old files:_ leave v1 files untouched as backups; never delete them in this release. Other prepared-account files are handled per C7: their drafts and pending completion titles become recovery copies in the device workspace, and nothing is sent to that other account. A file that fails to parse is listed in sync details as a preserved backup.
6. _Retry safely:_ an interrupted migration is retryable and idempotent, keyed by the source checksum. A corrupt source goes to `recovery`, never to a silent fresh workspace.

Legacy device notes (`WorkspaceService.ts:83-91`) import into the device workspace by the same category map. Unmapped notes become recovery copies.

### R3-1 — feasibility (blocking)

**Problem**

> The new 'newer edit wins' tie-break compares a client-clock timestamp (editedAt, set on the Mac, possibly weeks earlier while offline) with a server-clock, row-level updatedAt. In apps/web/src/db/schema.ts, Category.updatedAt is stamped by updatedAtColumn() on every update, so it reflects the latest change to ANY field (name, color, parentId, isDefault) and cannot say when the contested field was last changed. Example: the server renamed a category at T1, another field was recolored at T3, the local rename was edited at T2 with T1 < T2 < T3. The field-level conflict is on name, but updatedAt (T3) > editedAt (T2), so the older server rename wrongly supersedes the newer local rename, and the local operation is marked superseded and dropped. Client/server clock skew is also unaddressed (an offline Mac with a wrong clock flips the outcome). The rule that decides which user data is overwritten therefore rests on an unsupported timestamp comparison.

**Remedy**

> Define the comparison precisely: either track a per-field server change time (or a server revision) in base/server rows, or compare against the time the server value was first observed (base capture time on the same clock), and state clock-skew handling (for example server-time-only ordering, or editedAt clamped to the last server time seen). #### Section 4: Data Flow & Interaction Edge Cases

```
  edit category (local) → C17 validate → worker commit (local state) → [attached?] → C19 derive ops
      shadow: empty/30+ chars → refused name-taken-local/invalid-parent (no queue)
      shadow: default category → default-locked (C16)
      shadow: disk error → WorkspaceStorageError, UI keeps edit pending, C5 reason
  attach → syncBootstrap → merge vs base → ops → syncApply → outcomes (C8) → base/declined update
      shadow: bootstrap 401 → sign-in-to-sync; stale list → next refresh re-derives (idempotent)
```

Async ordering:

- _Invariant:_ derived ops never send with an `expected` older than the base they were derived from.
- _Schedule:_ refresh R1 derives ops O1. A local edit then commits E and re-derives O2, replacing O1, which is unsent. If O1 is already in flight, it is not replaced: C19 says in-flight ops settle first, and the merge reruns after the receipt.
- _Mechanism:_ the worker serializes commits, and the "in-flight" flag is set in the same transaction as the binding check (D1).
- _Regression proof:_ a controlled-pause test holds O1 in flight, commits E, and asserts that O2 waits until O1's receipt.

Sign-out vs in-flight follows C9 (bounded at 5 s, two orders tested).

Design-twice (new modules: `categoryMerge`, `migrateWorkspaceV1`, `category.syncApply`):

- _Shape A (chosen):_ the merge is a pure function `(local, server, base, declined, inFlight) → { localPatch, operations, detailRows }` inside the worker, so one owner holds the category state.
- _Shape B:_ the merge runs in main and the worker only stores results. That splits ownership of category state between main and the worker (red flag 5).
- A hides the whole conflict policy behind one call, so it is deeper.

Red flags:

- _(5) split ownership:_ the outbox is owned by the worker; the SyncLoop only reads sendable frozen payloads (EA3) → fixed.
- _(6) two ways:_ one sign-out (C23), one validator (C33), one benchmark script (EA12).
- _(7) importable internals:_ the D6 boundary test.
- _(8) hand-synced list:_ fixture state names live in one exported list, shared by DX2's page and its `--help` (EA16).

Realistic failure per new path:

- sign-out crash → EA1
- spoofed or mismatched identity → EA2
- lost batch response → EA3/EA4
